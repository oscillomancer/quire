# Stock plugins written as DSP scripts

Each folder here but `common/`, `suite/` and `template/` (the code they
share: `AGENTS.md`) is one stock plugin (ADR-0047): its DSP script in
`script/<name>.cpp`, and the product folder a source export makes from it,
which `plugins/CMakeLists.txt` builds from `plugins/template` with the
suite in `plugins/suite` (`supple_add_stock_script`). The plugin is the
script compiled as C++: no JIT, the same samples as the script in the
player, and every check the other stock plugins have.

## Files

- `script/<name>.cpp`: the plugin. Its DSP, parameters, factory patches
  and editor, in the language of `skill/guides/dsp-language.md`.
- `Catalog.cpp`: generated by a source export: the patch key of each
  `Param` member (C++ cannot see member names). `plugin.<name>.catalog`
  fails when it no longer matches the script; regenerate it with
  `cmake -DUPDATE=ON -DSANDBOX=build/dev/host/sandbox/quire-sandbox
  -DNAME=<name> -DDIR=plugins/<name> -DWORK=<scratch folder>
  -P plugins/catalog.cmake`.
- `product.cmake`: identity, kept by hand: AU codes, the parameter
  host-smoke turns (one that changes the sound at its default), and the
  CLAP features and extra outputs, which the plugin takes from the
  script's `Info` (`.features`, what the plugin is: Quire's plugin browser
  shows it after the name; `.outputs`, as `PRODUCT_AUX_OUTPUTS`) and
  `plugin.<name>.catalog` checks agree with a fresh source export.
  The state tag is the player's for the id, so sessions saved while the
  script ran in the player load in the native plugin.
- `Layer.cpp`, `Processor.h`, `Theme.h`, `targets.cmake`, `NOTICES.txt`: as
  a source export writes them; `targets.cmake` finds the suite beside it
  (`../suite`).
- `response.cmake` (optional): the plugin's own measurements through the
  built plugin, as `plugin.<name>.response`.
- `samples/` (optional): factory files, which `product.cmake` lists as
  `PRODUCT_ASSETS` and a script names as `factory:<name>`. Coppice's are
  rendered from Marram: `recipes.json` says how, and
  `tools/factory-samples/render.py plugins/<name>/samples/recipes.json`
  renders them again (`--check` compares them with the committed files),
  through the dev build's sandbox and Marram. They are first-party
  content, CC0 (`LICENSE` beside them).

## Changing one

1. Copy the script into a scratch library and give it a scratch `Info.id`
   (two plugins with one id are both listed), then iterate with the
   sandbox: `dsp.write`, `dsp.test` (with `patch` and `automation`),
   `dsp.preview` (with `pointer` steps). `quire-sandbox exec '<json>'
   --workdir <scratch>` runs them without MCP.
2. Put the change back in `script/<name>.cpp` with the real id. Keep every
   parameter key and the id: sessions and patches find them by name.
3. Build (`cmake --build build/dev --target plugin-<name>`), run
   `ctest -R plugin.<name>`, regenerate `Catalog.cpp` if a parameter came
   or went, and update the plugin's guide in `skill/guides/` and its section
   in `docs/specs/stock-effects.md`.
