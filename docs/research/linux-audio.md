# Linux audio survey, this workstation (2026-09-26)

Commands were read only except `/tmp/quire-jack-probe.c`, compiled and run for two seconds. The ordinary sandbox cannot connect to the user's PipeWire socket (`pw-metadata`: `can't connect: Operation not permitted`; `jack_client_open`: status `0x11`). Live results below used a one-command sandbox escalation against the existing session. No device or system configuration was changed.

## Kernel and real-time permissions

`uname -a`: `Linux archlinux 7.2.7-zen1-1-zen #1 ZEN SMP PREEMPT_DYNAMIC ... x86_64 GNU/Linux`. This is **not** the brief's assumed CachyOS RT kernel; `PREEMPT_DYNAMIC` does not establish PREEMPT_RT. `id`: `uid=1000(nate) ... groups=1000(nate),65534(nobody)`; no `audio` or `realtime` group. `ulimit -r`: `95`; `ulimit -l`: `unlimited`. `/etc/security/limits.d/99-realtime.conf` contains `@audio - rtprio 95` and `@audio - memlock unlimited`, although this process is not in that group. `pacman -Q rtkit`: `0.14-1`; `ps -eo comm,args` showed `rtkit-daemon`. The active high limit may come from another session mechanism; group policy alone does not explain it.

## PipeWire, JACK and ALSA

`pacman -Q`: PipeWire and pipewire-jack `1:1.6.9-1`, WirePlumber `0.5.17-2`, ALSA library `1.2.16.1-1`; `pacman -Q jack2` says not installed. `pkg-config --modversion jack libpipewire-0.3 libspa-0.2 alsa`: `3.1609.0`, `1.6.9`, `0.2`, `1.2.16.1`. `pw-metadata -n settings`: `clock.rate=48000`, `clock.allowed-rates=[44100,48000,88200,96000]`, `clock.quantum=1024`, min 32, max 2048, force rate/quantum 0. A single `timeout 2 pw-top -b -n 1` listed Dummy/Freewheel drivers, MIDI bridge, MOTU M4 input/output nodes, and other clients; its snapshot showed zero active QUANT/RATE rows, so the metadata and live JACK client are better evidence for the current buffer. `pw-jack` is installed, but `ldconfig -p` resolves system `libjack.so` to `/usr/lib/libjack.so`; `pacman -Qo /usr/lib/libjack.so /usr/include/jack/jack.h` says both are owned by `pipewire-jack 1:1.6.9-1`. Thus an ordinary dynamically linked JACK client works without the `pw-jack` wrapper in this session. The wrapper remains useful when overriding library paths for other clients. Headers exist under `/usr/include/jack` and `/usr/include/pipewire-0.3/pipewire`, with SPA headers under `/usr/include/spa-0.2/spa`.

`aplay -l` and `arecord -l` both returned `command not found`; `alsa-utils` is absent, so this survey cannot enumerate raw ALSA devices. `/dev/snd/seq` is absent in the sandbox, and this is not proof about the host outside it. Installed kernel ALSA headers define `SNDRV_SEQ_EVENT_UMP`, `SNDRV_SEQ_CLIENT_UMP_MIDI_1_0` and `_2_0` (`/usr/include/sound/asequencer.h`), so UMP API types are present; runtime ALSA sequencer availability was not verified. SPA headers have `SPA_MEDIA_SUBTYPE_midi` (`spa/param/format.h`), and `pw-top` showed `Midi-Bridge` and `bluez_midi.server`; these establish PipeWire MIDI components, not an end-to-end timestamp test.

## Two-second JACK probe

Source: `/tmp/quire-jack-probe.c`; compile command: `cc -Wall -Wextra -Wpedantic /tmp/quire-jack-probe.c -o /tmp/quire-jack-probe $(pkg-config --cflags --libs jack)`. It opens a client with `JackNoStartServer`, registers one audio output, zeros its buffer in `jack_set_process_callback`, counts `jack_set_xrun_callback`, queries both `jack_port_get_latency_range` directions, activates, sleeps two seconds, deactivates and closes. Run command: `/tmp/quire-jack-probe` (no `pw-jack`). Output: `buffer=1024 rate=48000 playback_latency=0..0 capture_latency=0..0` and `xruns=0`. The zero ranges are for an **unconnected** output port before activation; they must not be interpreted as measured device end-to-end latency. The client released its port/device when it exited. Initial sandboxed run failed `jack_client_open ... status=0x11`; the live-session run succeeded.

## DAW engine API trade-offs (recommendation, not ADR)

| API | Callback and RT ownership | Quantum/rate/device handling | Latency, MIDI, transport/offline | Client-library license |
| --- | --- | --- | --- | --- |
| JACK through pipewire-jack | `jack_set_process_callback`; JACK/PipeWire owns callback thread; small DAW integration surface. | `jack_set_buffer_size_callback` and `jack_set_sample_rate_callback`; request size with `jack_set_buffer_size`, but PipeWire graph/session policy may control actual values; observe reconfiguration. Device selection lives in PipeWire/WirePlumber, rather than in a JACK client. | Port latency range API, JACK MIDI port buffers, transport/freewheel callbacks. PipeWire compatibility and session manager semantics need validation for full transport/offline workflows. | `/usr/share/licenses/pipewire-jack/COPYING` begins “Copyright © 2018 Wim Taymans / Permission is hereby granted...” (MIT/X11 form). |
| Native PipeWire `pw_stream` / `pw_filter` | PipeWire data loop/process callbacks; app may integrate its own loop and node graph; more explicit control/metadata. | SPA buffer/format negotiation and param-change listeners; stream/node and metadata events for device/rate/quantum changes. Graph scheduler still governs actual quantum. | Native node/port latency params, SPA MIDI format and graph metadata; transport/offline behavior requires a DAW-owned model. Strong WirePlumber integration. | `/usr/share/licenses/pipewire/COPYING` is MIT-style; check precise linked subcomponents before shipping. |
| ALSA direct | App controls PCM I/O and its own thread/poll loop. | Direct hardware period/rate negotiation; device hotplug and resampling/routing/session policy become app responsibilities. | Hardware delay/timestamps and ALSA sequencer MIDI if available; DAW owns transport/offline. Bypasses PipeWire desktop routing and competes for hardware. | `alsa-lib` is LGPL-2.1-or-later (verify installed package terms before choosing; Quire policy requires human review for LGPL). |

Recommendation for prototyping: JACK through the installed PipeWire implementation is the shortest path to a callback-based DAW engine and was exercised here without `pw-jack`. Measure connected-port latency, rate/quantum changes, MIDI timestamping and freewheel behavior in a later probe; compare native PipeWire if session-manager/device control or transport limitations appear. Do not select the final API before those tests and an ADR.
