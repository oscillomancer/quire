## What improved, measured

- **No more exploding terms.** The campaign's worst reference losses were
  `5879` (acid-bass, a 23 ms attack against a 0 ms reference), `101.7`
  (fm-e-piano) and `47.4` (pad): all three were the unbounded envelope term.
  The worst loss this run is 34.1 (formant-lead, a structure task), and the
  corresponding attempts score 1.4–2.9 (acid-bass), 4.4–19.6 (fm-e-piano),
  3.3–3.7 (pad). Loss magnitudes are not comparable across the two runs (the
  loss function changed), but no single term can dominate by three orders of
  magnitude any more.
- **Tool errors down.** The campaign reported at least one tool error in 30/30
  attempts; this run, 14/30.
- **The optimizer is used and finds low in-session losses.** 89
  `optimize_start` calls across 30 attempts (campaign: 291-evaluation searches
  that never improved on the start, e.g. sub-bass stuck at 3.994 in all three
  attempts). Now sub-bass's in-session bests are 0.2472, 3.0631 and 0.0711 —
  the stall is gone.
- **Every failing attempt now spends the whole budget**: median wall 610 s
  against the campaign's 359 s, so part of the remaining failure is the
  10-minute limit, not a lack of progress.

## Why the pass count did not move: in-session loss ≠ scored loss

The decisive measurement is `reference.sub-bass-3`. Its agent ran
`optimize.start` (params: the amp envelope + level, target: the reference WAV,
phrase and `tail_s` identical to the scorer's) and the job reported
**best loss 0.0711**. The scorer rendered the captured patch in a fresh sandbox
and measured **3.5381**.

Replaying the agent's exact optimizer call in a fresh session reproduces 0.0711;
measuring that same patch in the *same* session (against the same reference
file) also gives 0.0711. Rendering the same patch in a *fresh* session gives
3.5381 — the scored number. Both numbers are deterministic. The whole
difference is one term:

| Where the patch was rendered | loss | envelope.decay20 term |
|---|---:|---:|
| agent's session (after the reference render, and inside the optimizer) | 0.0711 | 0.0235 |
| fresh session (what the scorer renders) | 3.5381 | 3.4518 |

The same pattern appears in `reference.sub-bass-1` (optimizer best 0.2472,
scored 2.0034).

Minimal reproducer (two sandboxes, ~1 minute; `python3` from the repo root with
the dev sandbox built, `tools/eval-harness` on `sys.path`):

```python
import sys; sys.path.insert(0, "tools/eval-harness")
from pathlib import Path
from common import Mcp, load_tasks, sandbox_command, setup

task = load_tasks("synth-reference", ["sub-bass"])[0]
start = dict(task["starting_patch"], seed=42)          # recipe: amp.release 80 ms
flat = {"params": {"amp.attack": 0.001042, "amp.decay": 256.198095, "amp.sustain": 99.997281,
                   "amp.release": 198.32985, "amp.level": 0.82515}}  # the optimizer's answer
render = dict(task["render"], notation=task["phrase"])

def go(label, pre_render):
    work = Path("build/repro") / label; work.mkdir(parents=True, exist_ok=True)
    with Mcp(sandbox_command(work), work) as c:
        setup(c, task, 42)
        c.call("patch.set", {"instance": "in_1", "patch": start})
        if pre_render:
            c.call("render", render)                    # a render before the change
        c.call("patch.merge", {"instance": "in_1", "patch": flat})
        path = Path(c.call("render", render)["path"])
        rep = c.call("analyze", {"source": str(path.resolve()), "note_off_s": 2.0})["report"]
        print(label, "decay20_ms =", rep["envelope"]["decay20_ms"])

go("after_a_previous_render", True)    # prints 348.0
go("fresh_session", False)             # prints 585.0
```

Concretely: the two renders differ **only in the first ~40 ms** (1870 of 211456
samples, max |Δ| 2.0e-2, RMS 5.3e-4; identical to the last bit afterwards), yet
`analyze` reports `envelope.decay20_ms` 348 vs 585. So an onset-only render
difference becomes a large envelope-descriptor difference, and the reference
loss amplifies it by 3.4 — enough to turn a "0.07" into a failure.

Two candidate mechanisms, not yet separated (this is where a follow-up should
start):

1. the render itself: a render that follows another render (or a flat
   `params` merge) in the same instance has a different first ~40 ms than the
   first render of a fresh instance — the P3.4a class of state leakage, at
   least partly still present; the flat `{"params": {...}}` merge path (what
   `optimize.start`'s result patch and each optimizer candidate use) is
   affected, while a full `patch.set` of the same patch is not;
2. the analysis: with the audio identical beyond 40 ms, `decay20_ms` should not
   move by 237 ms; whether the analyzer's peak/onset anchoring makes it
   hypersensitive to the first frames needs checking against
   `docs/specs/core-analysis.md`.

Either way the practical consequence is the same and it is a blocker for
reading this suite: **the optimizer's search space is the in-session render,
the scorer's is a fresh render, and for these patches they disagree by a factor
of 50 in the loss.** An agent can reach 0.07 in its session and still score
3.5. Until that is understood, the reference suite measures this artifact as
much as it measures search quality.

## Caveats

- 30 attempts, one model, one seed, one build. Differences of one or two passes
  are not significant; the per-task patterns (tier-1 short tasks pass, tier-2/3
  mostly fail) are the same as the campaign's.
- The loss changed between the two runs (log-time envelope terms), so do not
  compare loss medians across them; compare pass counts and the term breakdown.
- The agent prompts changed in the same window (`compare` reports `loss.total`,
  the preamble states the pass threshold), so this run is "all of P3.4a–P3.4d",
  not one change at a time.
