# B2: REAPER capacity comparison

**Result (2026-10-21, REAPER 7.82, same machine/device/session as B1, Marram
as the synth, kernel 7.2.9-rt3):** REAPER with its default anticipative FX
passed N = 83 once and failed its confirmation with two underrun-timestamp
changes; N = 82 passed and N = 84 failed (4), so its capacity is 82 to 83
tracks. Quire with anticipation sustains a confirmed **75** and without it
28 to 29 ([b1.md](b1.md)): REAPER is ahead by about 10 %. The xrun column
counts changes of REAPER's last-underrun timestamp between polls, a coarser
count than B1's server xruns.

The 2026-10-01 row ran REAPER 7.81 and Orrery on kernel 7.2.7-zen1, where REAPER failed at
N = 1 (an underrun within 300 s), like Quire without anticipation, while
Quire with anticipation sustained 30. That run saw two timestamp changes but
the timestamp ended at 0, so at least one underrun occurred and the second
change may have been a reset.

Two harness bugs were fixed before the 2026-10-01 run: REAPER's Linux audio modes are
0 JACK / 2 Dummy / 3 PulseAudio (the private configs had used 1 and 3), and
play pressed right after `Audio_Init` was stopped by the device's own startup
(the script now lets the device settle for a second).

The RPP uses B1's exported notation MIDI and CLAP states for the synth (Orrery
in rows before 2026-10-21, Marram since), the EQ
(Facet in rows before 2026-10-18, Yarrow since) and the compressor (Ballast
in rows before 2026-10-19, Sundew since), including the monitored track and
the master's peak control. No ReaEQ/ReaComp
substitutions are made. REAPER's anticipative FX preferences stay at default.
Offline renders prove generation/loading and are not capacity measurements.
The xrun count is observed changes to audio/media underrun timestamps; see
the guide for its polling limitations.
